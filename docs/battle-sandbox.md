# Battle sandbox contract (v1)

The reviewed architecture selects a supervised native `battle_runner` over either launching a process for each Go or reusing a live scenario. The runner loads pinned authored content into private memory and never constructs `Engine` or connects to Redis. The browser edits and plays back drafts; only Rust decides combat outcomes. Next verifies developer access, captures revisions, and forwards requests over a user-private Unix socket. A signed developer identity has no relationship to player login.

## Editor and lifecycle

Content → Battle opens the editor after developer unlock. Team A/B and a searchable pinned catalog configure placement; select by board or roster, drag or enter coordinates, and remove explicitly. Use a centered 12,000 × 8,000 rectangle (try starts within 2,000 for short-range units); Close Quarters is 500 × 500. Invalid bounds or moves retain the last valid draft, with affected placement IDs identified. Named variants are shared only by placements that reference them; show base and effective values and allow per-field reset. Acquisition and firing ranges are separate; dismantle uses hull contact plus tolerance. Saves stay in this browser with overwrite confirmation and quota errors. Reopen by exact revision, never by falling back to current content.

Go freezes the current draft, including unsaved edits. The UI distinguishes submission, acceptance, rejection, capacity/unavailability, simulation failure, win/draw, tick limit, and unavailable replay. Status lookup failures can be retried for the same run. Once ready the replay opens paused at tick 0. Play/pause, speed and seek change only the local cursor. Reset restores the exact pre-Go draft and invalidates the current submission generation. Guard every async result by generation and, after acceptance, run ID. Announce lifecycle changes rather than every tick. Distinguish teams with labeled markers as well as color, with a roster for overlap and a marker for missing art. Under `prefers-reduced-motion: reduce`, the decorative launch flash is hidden; shot positions, contact/expiry/casualty markers, and the event log remain.

## Wire contract

All browser routes are under `/api/content/battle`, gated in development by the signed developer session (except `POST /session`, which exchanges the configured key for that session). Writes require the configured same origin. JSON errors carry `code` and `message`; unknown, expired, and foreign run IDs have the same unavailable response.

- `POST /catalog` captures current authored YAML/art in the sandbox-only revision root; `GET /catalog?revision=…` loads an exact retained hash. Returns the revision and normalized unit entries (base combat stats, hull, strategy, weapon IDs/types, optional pinned art). Art URLs stay behind the same gate.
- `POST /` takes `{version:1, revision, bounds:{width,height}, placements, variants}`. A placement is `{id, team:"a"|"b", type_id, x, y, variant_id?}`. A variant is `{id, name, type_id, health?, speed?, acquisition_range?, weapons:[{id,damage?,range?,cooldown_ticks?}]}`. Placement order determines simulation IDs and is preserved on save. IDs in the draft are distinct within each list. Rust validates resolved stats and references, independently of the editor. A successful enqueue returns HTTP 202 and `{run_id}` (dashed UUID), not a result.
- `GET /[runId]` returns the ID and status: `pending`, `rejected`, `failed`, or `ready`. Ready includes `tps`, `last_tick`, `outcome` (`a`, `b`, `draw`, `tick_limit`), and `page_count`. Rejected/failed includes the reason.
- `GET /[runId]/replay?page=0` returns `{run_id, page, frames}`. Frames carry tick-indexed hull poses and health, active shot positions, and events (laser endpoints, kinetic launches, sweep terminations with reason/contact and tick fraction, and attributed casualties). Frames may also carry `hull_motion` entries `[id, start, stop, fraction]` when a pursuit snap or wall clamp makes the tick non-linear; interpolate from `start` to `stop` over `fraction` of the tick, then hold `stop` for the remainder. Tick 0 is the setup before actions. Numeric simulation IDs correspond to 1-based placement order; projectile IDs in the replay use a separate small sequence. Playback interpolates only visuals.

## Step and bounds

Use production `GAME_TPS`/friction. Both binaries call the engine's `load_env`, which loads the engine package's `.env` before the cwd-relative and root `.env` files; a service-local `GAME_TPS`/friction therefore wins for the live engine and the sandbox regardless of the launch directory. The runner also pins its working directory to the engine package for workspace and socket discovery. Run autonomous combat against the pre-step positions, remove instant casualties, capture hull starts, integrate, sweep existing projectiles and remove kinetic casualties, then append new shots. End when a team is eliminated and remaining shots have finished (or at the cap, with no winner awarded at the cap if unresolved). No economy, radiation, fog, or direct player orders.

Whole hulls stay in the closed arena: the first wall contact zeros velocity and is represented in the shared sweep as motion followed by stationary time. Kinetic shots sweep only to the earlier of first exit or remaining travel. Contact at a positive clipped endpoint counts; outward shots already at the boundary expire immediately. Lasers are unchanged. The live sweep is the unbounded specialization, with no sandbox recording or edge work.

128 KiB draft body, 64 placements/variants, 2,400 ticks, 256 active shots per run, two running jobs and no waiting queue. Replay includes tick 0, is byte-capped per run and globally, paged, and expires. Capacity violations fail explicitly rather than truncating events. No replay or run state survives runner restart; saved setups and retained bundles are separate.

The editor and runner limit arena dimensions to 1–20,000 world units, editable speed/ranges to 20,000, health/damage to 1,000,000 HP, and editable cooldowns to 1–2,400 whole ticks. The runner also caps inherited hull radius, contact tolerance, weapons per unit, projectile speed, distance, and spread before stepping. It uses two simulation workers per worktree, with a separate serialized catalog load. There are no new allocations, scans, serialization, or I/O in the live tick; wall checks and replay capture run only in the sandbox.

Pinned capture and reads cap the authored YAML and retained manifest at 512 KiB each, individual assets at 2 MiB, and referenced art at 16 MiB per revision. Capture shares the authored-files lane with the content editor to avoid torn snapshots, but never imports the Redis publisher or stages in the live revision root.

## Integration verification

With the filtered dev stack from the README, open Content → Unlock Battle. Apply Close Quarters; place `fighter_v1` for A at (−110, 0) and `kinetic_fighter` for B at (110, 0); place a spare unit, drag or move it via X/Y, then remove it. Try shrinking until a hull no longer fits. Create a laser variant for A, change damage and cooldown, save under a name, reload, and reopen it. Confirm coordinates, teams, overrides, bounds, and revision. Make an unsaved edit before Go. Run, pause, change speed, scrub across a casualty both ways, then Reset; the unsaved edit must be restored. Repeat unchanged and compare replay frames, ignoring the run ID.

In a disposable setup, also verify a missing revision, an expired or foreign run, cross-origin and unauthenticated requests, oversized bodies, worker saturation and shutdown. Delay an older submit/status/replay response while using Reset and a newer Go; it must not replace the current run. Use the focused `sandbox_matches_the_production_laser_and_kinetic_phases`, `bounded_sweep_accepts_contact_at_the_wall_but_nothing_past_it`, and `run_waits_for_the_eliminated_teams_shot_and_replays_deterministically` Rust fixtures for phase, edge, and determinism checks.

### Observed results (2026-11-27)

A disposable private stack was used: Next dev on port 34123 with `BATTLE_ORIGIN=http://localhost:34123`, and the native `battle_runner` on its worktree socket. No Redis or live-engine process was started. A service-local `services/rts-engine/.env` set `GAME_TPS=37`; a throwaway `GameConfig::from_env` probe printed `37`, and every run status (including one from a runner launched at the repository root) reported `tps: 37`. `cargo check -p rts-engine --tests` compiled the focused fixtures.

- **Flow:** Content → Unlock Battle accepted the configured key and showed pinned revision `a92f31…`. Close Quarters produced 500 × 500. `fighter_v1` A at (−110, 0) and `kinetic_fighter` B at (110, 0) placed by coordinates; a `worker` was placed, moved to (40, 40) by X/Y, and removed. Shrinking to 100 × 100 was refused, naming both displaced fighters, while the draft stayed at 500 × 500.
- **Variants and saves:** “Laser A” was created for the A fighter with damage 8 and cooldown 10 ticks. “Duel A” saved, the page was reloaded, and the setup reopened with the same revision, bounds, teams, coordinates, and overrides.
- **Run and replay:** An unsaved move of B to (110, 20) was included in Go. The replay opened paused at tick 0 with “Team B wins”, 37 TPS, and 5 frames. Play/Pause, 4× speed, seek to tick 4 (contact and casualty events shown), backward to tick 2 (both hulls alive), and forward again all behaved. Reset restored B at (110, 20) and the unsaved marker exactly.
- **Stale response:** The first run's status request was delayed by 8 s; Reset then a second Go produced a new replay. The delayed request was aborted, and after the delay expired the second replay was still current.
- **Determinism and isolation:** The same draft submitted twice concurrently (while both jobs ran) produced byte-identical replay pages after removing `run_id`; both reported `outcome: b`, `last_tick: 4`, `tps: 37`.
- **Access and bounds:** Without the session, status returned 401; cross-origin submit returned 403; a second developer session reading the first session's run returned the same 404 body as an unknown run; a malformed run ID returned 404. A 129 KiB body returned 413; width zero returned 400; a missing revision returned 202 then `rejected` naming the hash; a variant attached to the wrong base type returned 202 then `rejected`. Six simultaneous submits produced two 202 and four 429; both accepted 2,400-tick runs completed as `tick_limit`, then capacity was free again. Killing the runner returned 503; after restart the old run returned 404 and a new submit completed. Invoking the submit handler with `NODE_ENV=production` returned 404 `battle_unavailable`.
- **Wall stop and reduced motion:** A disposable pinned revision gave the A fighter the authored `flee` strategy (shipped content has no flee unit). At 0.25× playback the hull moved from 50 to 150 and held 150 after tick fraction 0.1865. A nonlethal kinetic contact at tick 7 fraction 0.441 rendered its gold marker at x = 50.2 with the hull center at 150 and 900 HP; seeking 7 → 0 → 7 reproduced the same marker. With reduced motion emulated, the launch ring computed `display: none`, while the shot dot, contact marker, and event log remained.
- **Pre-hydration form:** The server-rendered unlock form has `method="post"`, a disabled unnamed password field, and a disabled button; no `battleKey` control appears in SSR output.
